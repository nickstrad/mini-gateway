## Release It! checklist

- **Integration points:** Covered — coalescer flights carry a virtual-clock deadline (`tCoalesce`, `timeouts.statement`) independent of any waiter; the database-silent path is exercised by `coalesce-shared-error-{strict,relaxed}` (2 s read vs 500 ms statement deadline).
- **Blocked threads:** Mostly covered — on reply, error, deadline, last-leaver cancel/vanish, and shutdown, leases return through normal release or the dirty-connection table and `Quiesce()` asserts zero in use; however, Finding 2 shows `Shutdown` can still lend an idle DB connection to a newly promoted held flight mid-shutdown before closing it.
- **Slow responses:** Covered — waiter cancel/leave updates reference count (`WaiterOwnError`/`WaiterGone`, `CancelsCoalesced`); only the last leaver cancels DB work (`Cancelled`, `CancelsForwarded` or `EndVanishedMidStatement`); flight deadline sends `08006`/`08007` or `53M01` and routes running leases to the dirty table; `53M04` cap refusals are answered immediately in O(1).
- **Cascading failures:** Covered — the breaker sits ahead of the coalesce stage (`lease.go:35-40`), so with the database down requests fail fast in O(1) without touching the coalescer; when the breaker opens with a queued flight, `refuseWaiting` calls `coalRefused` so all waiters receive `53M03`; health stays `degraded` (from pool/engine), never `failed`.
- **Chain reactions:** Not applicable directly to a single-instance coalescer (3-instance kill is chunk 13), and the coalescer sits before the admission queue so shedding remains controlled by the queue stage without unbounded queuing (`MaxWaiters` refuses with `53M04`, `MaxFlights` passes unshared).
- **Dogpile:** Covered — a failed flight shares its error once with all waiters (`coalesce-shared-error-*`, ≤ 2 DB reads for 100 waiters, recovery step asserted); no automatic re-drive loop exists in the coalescer.
- **Self-denial attacks:** Covered — replies are stored once and written as a single slice reference to each waiter; `MaxWaiters` caps fan-out per flight; `MaxReplyBytes` caps stored bytes; `MaxFlights` caps active keys; no-share list is a fixed ring (`NoShareMax`).
- **Force multiplier:** Not applicable here because the coalescer has no automatic retry or adaptive feedback loop; strict mode holds at most one next flight per key.
- **Unbalanced capacities:** Covered — `MaxFlights`, `MaxWaiters` (`53M04`), `MaxReplyBytes` (validated ≤ `ReplyBufferCap/2`; detaches and lists on no-share), `NoShareMax` (evicts oldest), `HotKeys` (≤ 64, Space-Saving replacement), `MaxTenantStats` (4,096, folds to `other`), all documented in `docs/capacity-table.md`.
- **Scaling effects:** Covered — `NOTES.md` states the fleet row (1–2 reads weakens to ≤ N per burst at N instances, prepared for chunk 13); Prometheus/CSV labels are bounded (`hot_key_hits` exports rank only, never SQL text; `tenant_hits` uses the bounded tenant label).
- **Users:** Covered — `MaxWaiters` bounds per-flight fan-out with `53M04`; `key_scope: tenant` isolates per-tenant flights; per-tenant hit stats are bounded at 4,096 + `other`.
- **Unbounded result sets:** Covered — `req.stored` is capped at `coalesce.max_reply_bytes` (≤ half `limits.reply_buffer`); past the cap, followers receive `53M04` (nothing sent to them) and the owner switches to ordinary back-pressured streaming (`req.relayed > 0`), so a subsequent DB failure closes the owner (`ErrRowPartialReply`) instead of delivering a truncated reply.
- **Compounds:** Defect found (Finding 1) — the compound interaction of a strict-mode coalesced flight expiring while waiting in `AdmissionQueue` causes `coalExpireOwner` to call `RemoveAt` + `shed`, breaking `admission.ShedCount() == engine.Shed` (`Engine.Invariants()`). Also Finding 2 (`Shutdown` + strict held flight promotion).
